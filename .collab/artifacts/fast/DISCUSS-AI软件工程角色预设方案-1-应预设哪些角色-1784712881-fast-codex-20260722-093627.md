下面给出一套可落地的 **AI 软件工程角色预设方案**。核心原则是：

> **角色定义与模型选择解耦。**  
> 角色描述“要完成什么、遵循什么标准、交付什么”；模型适配描述“由哪个模型、使用哪些工具、以什么参数执行”。

不要把角色简单写成“你是一位资深工程师”。高质量角色 Prompt 应当是一份可验证的“岗位契约”。

---

# 一、应预设哪些角色？

不建议一开始设计十几个自治 Agent。多数团队先预设 **6 个核心角色**，再根据项目风险增加专项角色。

## 1. 核心角色

| 角色 | 核心职责 | 主要交付物 | 不应负责 |
|---|---|---|---|
| 需求分析师 / Product Analyst | 澄清需求、识别歧义、制定验收标准 | 需求说明、用户故事、AC、边界条件 | 直接决定技术实现 |
| 软件架构师 / Architect | 模块划分、接口、数据流、技术权衡 | 架构方案、ADR、接口草案、风险清单 | 大量具体编码 |
| 实现工程师 / Developer | 按任务和约束编写、修改代码 | Patch、迁移脚本、实现说明 | 自行降低验收标准 |
| 代码审查员 / Reviewer | 检查正确性、回归风险、可维护性 | 分级 Review 意见、阻塞项、建议项 | 未授权直接重构整个项目 |
| 测试工程师 / QA | 设计测试、验证边界和异常路径 | 测试计划、测试代码、复现步骤 | 仅检查“能否编译” |
| 交付工程师 / DevOps | CI/CD、环境、发布、回滚和可观测性 | Pipeline、部署配置、Runbook | 无审批操作生产环境 |

## 2. 按需增加的专项角色

### 安全审查员

适用于支付、身份认证、隐私数据、供应链、互联网入口等场景。

职责包括：

- 威胁建模；
- 权限边界检查；
- 注入、越权、密钥泄露检查；
- 依赖和供应链风险检查；
- 给出可验证的修复方案。

### 数据库工程师

适用于复杂查询、数据迁移、高并发、数据一致性问题。

重点检查：

- Schema；
- 索引；
- 锁和事务；
- Migration 可回滚性；
- 数据兼容和零停机发布。

### 性能工程师

适用于延迟、吞吐量、资源成本有明确 SLO 的项目。

重点输出：

- 性能假设；
- 基准测试方法；
- Profiling 结果；
- 性能回归门槛。

### 文档工程师

负责：

- README；
- API 文档；
- 变更说明；
- 运维手册；
- 示例和迁移指南。

### 项目协调器 / Orchestrator

它不应亲自完成所有工作，而是：

1. 分解任务；
2. 选择角色；
3. 管理依赖；
4. 汇总结果；
5. 触发复审；
6. 在信息不足时请求人工决策。

# 二、推荐的角色协作流程

一个常规功能可以采用：

```text
需求分析
   ↓
架构设计
   ↓
任务拆分
   ↓
代码实现
   ↓
测试 + 代码审查
   ↓
安全/性能专项检查（按风险触发）
   ↓
交付与文档
```

建议遵循两个控制原则：

## 1. 实现者不能自我批准

至少在高风险变更中，应将以下职责分离：

- 写代码；
- 审查代码；
- 批准发布。

即使使用的是同一种模型，也应使用：

- 不同上下文；
- 不同角色 Prompt；
- 独立检查清单；
- 最好不同模型或不同运行实例。

## 2. 角色按风险触发，而不是全部并行

例如：

| 变更类型 | 必须触发的角色 |
|---|---|
| 文案修改 | Developer + Reviewer |
| 普通业务功能 | Analyst + Developer + QA + Reviewer |
| 数据库迁移 | Architect + Developer + DBA + Reviewer |
| 登录/支付/权限 | Architect + Security + QA + Reviewer |
| CI/CD 修改 | DevOps + Reviewer |
| 性能关键链路 | Architect + Performance + QA |

这样可以避免多 Agent 讨论成本超过开发成本。

# 三、角色 Prompt 如何精确提取？

角色 Prompt 不应依靠一次性的自然语言创作，而应从组织资料和工程约束中结构化提取。

## 1. Prompt 信息来源优先级

建议按以下优先级采集：

1. 法律、合规和安全要求；
2. 组织级工程规范；
3. 仓库内规则，例如 `AGENTS.md`、`CONTRIBUTING.md`；
4. 项目架构文档和 ADR；
5. CI、Lint、测试、部署规则；
6. Issue、任务说明和验收标准；
7. 团队惯例；
8. 模型自行推测。

最后一项必须显式标记为“假设”，不能伪装成项目事实。

## 2. 将资料拆成“原子规则”

不要直接把几十页规范全部塞进 System Prompt。应把内容拆成可执行、可验证的规则。

例如，原始描述：

> 服务需要保持兼容，数据库修改应尽可能安全，测试要完整。

应转换为：

```yaml
rules:
  - id: API-001
    condition: 修改公开 HTTP API
    requirement: 不得删除或重命名已有响应字段
    severity: blocking
    verification: 运行 contract test

  - id: DB-003
    condition: 修改数据库 schema
    requirement: migration 必须支持滚动发布，不得在单次事务中重写大表
    severity: blocking
    verification: 检查 migration 和 rollback 方案

  - id: TEST-002
    condition: 修复缺陷
    requirement: 必须新增至少一个能够在修复前失败的回归测试
    severity: blocking
    verification: 展示测试名称及覆盖路径
```

“尽可能安全”“代码优雅”“测试完整”等表述无法稳定执行，必须转换成可观测条件。

## 3. 对规则分类

每条规则至少应标注：

- `scope`：适用范围；
- `trigger`：触发条件；
- `severity`：阻塞或建议；
- `source`：规则来源；
- `verification`：验证方法；
- `owner`：谁负责执行；
- `reviewer`：谁负责复核。

例如：

```yaml
id: SEC-AUTH-01
scope: backend
trigger: 变更认证或授权逻辑
severity: blocking
source: security-standard.md#authorization
owner: developer
reviewer: security-reviewer
requirement: 所有对象访问必须验证当前主体对目标对象的权限
verification:
  - 新增跨租户访问负向测试
  - 检查查询条件是否包含 tenant_id
```

## 4. 处理规则冲突

建议采用明确的优先级：

```text
系统安全约束
> 法律和合规
> 组织规则
> 仓库规则
> 当前任务要求
> 角色默认偏好
> 模型自行判断
```

遇到冲突时，角色不能静默选择，应输出：

```text
发现冲突：
- 任务要求删除旧接口；
- 仓库兼容性规则禁止在当前主版本删除公开接口。

建议：
1. 保留旧接口并标记 deprecated；
2. 在下一个 major version 删除；
3. 如需立即删除，请由负责人显式批准。
```

# 四、标准角色 Prompt 结构

推荐把角色 Prompt 固定为以下结构。

```yaml
role:
  name: Code Reviewer
  mission: 识别本次变更中的正确性、回归、安全性和可维护性问题

scope:
  included:
    - 检查 diff
    - 检查相关调用链
    - 检查测试覆盖
  excluded:
    - 未经请求重写整个模块
    - 基于个人风格提出阻塞意见

inputs:
  required:
    - task_description
    - acceptance_criteria
    - git_diff
    - repository_rules
  optional:
    - test_results
    - architecture_docs

workflow:
  - 理解需求和验收标准
  - 定位变更影响范围
  - 检查正确性和边界条件
  - 检查兼容性、安全性、并发和错误处理
  - 检查测试是否能捕获实际回归
  - 按严重等级输出结论

output_contract:
  format: markdown
  fields:
    - summary
    - blocking_findings
    - non_blocking_findings
    - test_gaps
    - residual_risks

finding_schema:
  - severity
  - file
  - line
  - problem
  - evidence
  - impact
  - recommended_fix

constraints:
  - 不虚构未读取的文件内容
  - 没有证据时使用“可能”并说明验证方法
  - 仅评论本次变更引入或明显暴露的问题
  - 不把纯代码风格偏好标为阻塞问题

completion_criteria:
  - 每个阻塞项都包含定位、影响和可执行修复建议
  - 明确说明是否建议合并
```

# 五、一个可直接使用的代码审查角色 Prompt

```text
你是本仓库的代码审查员。

目标：
识别当前变更引入的、会影响正确性、安全性、兼容性、性能或可维护性的具体问题。

工作步骤：
1. 先读取任务描述、验收标准和仓库规则。
2. 阅读变更 diff，并在必要时追踪调用方、被调用方、类型定义和测试。
3. 重点检查：
   - 正常路径和异常路径是否正确；
   - 空值、边界值、并发、重试和部分失败；
   - API、数据库和配置兼容性；
   - 身份认证、授权、输入验证和敏感信息；
   - 测试是否能在错误实现下失败。
4. 仅报告具有明确证据且可操作的问题。

每个问题必须包含：
- 严重等级：P0/P1/P2/P3；
- 文件及行号；
- 问题描述；
- 触发条件或复现路径；
- 实际影响；
- 推荐修复方式。

严重等级：
- P0：可能造成灾难性生产事故或严重安全事件；
- P1：会导致主要功能错误、数据损坏或明确漏洞；
- P2：在特定条件下产生错误或显著维护风险；
- P3：非阻塞改进。

限制：
- 不要将个人风格偏好报告为缺陷；
- 不要报告与本次变更无关的既有问题，除非该变更显著扩大了风险；
- 不确定时明确说明假设和验证方式；
- 如果没有发现值得报告的问题，直接说明“未发现阻塞问题”，不要凑数。

最终输出：
1. 审查结论；
2. 阻塞问题；
3. 非阻塞问题；
4. 测试缺口；
5. 剩余风险；
6. 是否建议合并。
```

# 六、如何判断 Prompt 是否“精确”？

使用四个指标。

## 1. 可执行性

模型是否能根据 Prompt 明确知道下一步做什么？

错误：

> 认真审查代码，确保最佳实践。

正确：

> 检查 diff 以及直接调用链；每个问题必须包含文件、行号、触发条件和影响。

## 2. 可验证性

输出能否由测试、静态检查或人工复核？

错误：

> 架构应当合理。

正确：

> 新模块不得形成循环依赖；使用依赖图检查，并列出新增依赖边。

## 3. 边界清晰度

必须写明：

- 做什么；
- 不做什么；
- 何时停止；
- 何时请求人工决策。

## 4. 输出稳定性

应指定固定 Schema，而不是让模型自由发挥。

例如：

```json
{
  "decision": "approve | request_changes | needs_information",
  "findings": [
    {
      "severity": "P1",
      "file": "src/auth.ts",
      "line": 84,
      "problem": "...",
      "evidence": "...",
      "impact": "...",
      "recommendation": "..."
    }
  ],
  "test_gaps": [],
  "assumptions": []
}
```

# 七、角色与 Claude、Codex、Gemini 如何匹配？

不建议形成永久固定的“一角色一模型”关系。模型版本和工具能力会持续变化，应该采用：

```text
角色规范
+ 任务特征
+ 模型能力
+ 工具权限
+ 成本/延迟要求
= 动态路由
```

以下是一般性的起始匹配，最终应以团队实测为准。

## 1. Claude

通常适合作为：

- 需求分析师；
- 架构师；
- 复杂方案评审者；
- 安全威胁建模辅助；
- 长文档整理者；
- 跨文件语义分析者。

常见优势场景：

- 需求含大量业务背景；
- 需要比较多个方案并解释权衡；
- 需要处理长规范、ADR、设计文档；
- 需要产出清晰的人类可读说明。

需要控制的地方：

- 架构论述可能过长；
- 可能提出超出当前任务范围的重构；
- 必须通过输出契约限制“泛化建议”。

## 2. Codex

通常适合作为：

- 实现工程师；
- 代码审查员；
- 缺陷修复工程师；
- 测试编写者；
- 仓库级修改执行者；
- CI、脚本和工程配置修改者。

常见优势场景：

- 需要直接读取和修改代码仓库；
- 需要运行测试、Lint、构建工具；
- 需要生成较小、可审查的 Patch；
- 需要根据实际代码定位调用链；
- 需要检查 diff 中的具体缺陷。

尤其适合将任务写成：

```text
定位 → 修改 → 运行验证 → 汇报结果
```

需要控制的地方：

- 限定允许修改的目录；
- 明确是否允许安装依赖；
- 明确测试和命令权限；
- 要求避免顺手重构；
- 对删除、迁移、生产操作设置人工审批。

## 3. Gemini

通常适合作为：

- 多模态需求分析师；
- UI/UX 实现辅助；
- 图表、截图、设计稿分析者；
- 大规模资料整理者；
- Google 技术生态相关开发辅助；
- 视频、图片、文档混合输入分析者。

常见优势场景：

- 输入包含界面截图、设计稿、流程图或视频；
- 需要从视觉稿提取组件和状态；
- 需要分析大量异构资料；
- 项目与 Android、Firebase、Google Cloud 等生态紧密相关。

需要控制的地方：

- 从截图推断的尺寸、交互不能直接视为事实；
- 应区分“视觉观察”“推断”“需求确认项”；
- UI 生成后仍要通过浏览器测试和视觉回归验证。

# 九、不要为不同模型复制三套角色 Prompt

推荐使用“核心角色 + 模型适配器”。

## 1. 核心角色层

与模型无关：

```yaml
role: developer
goal: 按验收标准完成最小必要修改
required_outputs:
  - changed_files
  - implementation_summary
  - verification_results
constraints:
  - 不修改无关文件
  - 不跳过失败测试
```

## 2. 模型适配层

针对模型和运行环境补充：

```yaml
adapter:
  model_family: codex
  tools:
    - repository_read
    - repository_write
    - shell
  execution_policy:
    - 修改前先读取相关文件
    - 修改后运行目标测试
    - 禁止访问生产凭据
```

或者：

```yaml
adapter:
  model_family: gemini
  inputs:
    - screenshot
    - design_spec
  execution_policy:
    - 将观察事实与推断分开
    - 输出组件树和响应式行为
```

这样更换模型时，不需要重写组织角色规范。

# 十、模型路由的量化方式

可以为每个任务提取特征：

```yaml
task_features:
  repository_editing: 5
  long_context: 3
  multimodal: 0
  architecture_reasoning: 4
  tool_execution: 5
  latency_sensitivity: 2
  security_risk: 4
```

然后计算：

```text
ModelScore =
能力匹配度 × 0.35
+ 工具匹配度 × 0.25
+ 历史成功率 × 0.20
+ 质量评分 × 0.10
+ 成本评分 × 0.05
+ 延迟评分 × 0.05
```

高风险任务还应增加硬约束：

```text
如果 security_risk >= 4：
- 必须经过独立安全审查；
- 不允许实现 Agent 自行批准；
- 必须保留测试和命令执行记录；
- 生产变更需要人工确认。
```

# 十一、如何用评测而不是印象选择模型？

建立团队自己的任务集，至少包含：

1. 一个普通功能开发；
2. 一个跨文件缺陷修复；
3. 一个并发或事务问题；
4. 一个 API 兼容性审查；
5. 一个安全漏洞修复；
6. 一个数据库迁移；
7. 一个 UI 截图实现；
8. 一个 CI 故障定位；
9. 一个长需求转技术方案任务；
10. 一个“信息不足，应主动提问”的任务。

评价指标：

| 指标 | 说明 |
|---|---|
| Correctness | 最终实现是否正确 |
| Test pass rate | 测试通过率 |
| Regression rate | 是否引入回归 |
| Review precision | 报告的问题中有多少是真问题 |
| Review recall | 已知缺陷中发现了多少 |
| Patch minimality | 是否只做必要修改 |
| Instruction compliance | 是否遵守仓库和任务约束 |
| Tool reliability | 命令、测试、修改是否可靠 |
| Cost | 单任务成本 |
| Latency | 完成时间 |
| Human rework | 人工返工量 |

尤其是代码审查，应同时看：

```text
Precision = 真问题数 / 模型报告问题总数
Recall = 模型发现的已知问题数 / 预埋问题总数
```

只看“输出是否显得专业”会严重误判模型能力。

---

# 十二、建议的最小可行配置

如果团队刚开始，可以先配置以下 6 个角色：

```yaml
roles:
  - analyst
  - architect
  - developer
  - reviewer
  - qa
  - devops
```

模型初始路由：

```yaml
routing:
  analyst:
    primary: claude
    fallback: gemini

  architect:
    primary: claude
    fallback: codex

  developer:
    primary: codex
    fallback: claude

  reviewer:
    primary: codex
    fallback: claude

  qa:
    primary: codex
    fallback: gemini

  devops:
    primary: codex
    fallback: claude

  multimodal_ui:
    primary: gemini
    fallback: codex
```

高风险复核可以采用异构模型：

```text
Codex 实现 → Claude 做架构/安全复核
Claude 设计 → Codex 根据仓库实际结构验证可实现性
Gemini 从设计稿提取 UI → Codex 落地代码并运行测试
```

异构复核的价值不是“哪个模型绝对更强”，而是减少相同模型重复同一种盲点。

# 十三、最终建议

1. **先定义角色契约，再选择模型。**
2. 每个角色必须包含目标、输入、流程、边界、输出格式和完成条件。
3. 把模糊规范转换为带触发条件和验证方法的原子规则。
4. 角色 Prompt 保持模型无关，模型差异放在 Adapter 层。
5. 默认可采用：
   - Claude：需求、架构、长文档和权衡分析；
   - Codex：仓库操作、实现、测试和代码审查；
   - Gemini：多模态、设计稿、视觉资料和 Google 生态。
6. 高风险任务必须实行实现、审查和批准分离。
7. 最终匹配必须根据团队真实任务集的成功率、返工率、成本和延迟动态调整，而不是依赖通用排行榜。
